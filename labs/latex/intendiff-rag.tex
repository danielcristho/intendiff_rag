\begin{abstract}[]
Package updates can introduce malicious behavior that resembles legitimate
software activity. This study evaluates whether a profile of the package's
purpose (intent) and in-context examples help small local large language
models (LLMs) distinguish the two. Six configurations were compared on six
open-weight models, using 129 updates labeled malicious from 98 campaign
clusters and 1,868 typical updates. Malicious labels come from the dataset
sources; typical updates are assumed benign after advisory filtering. For most
pairs, no capability signal was found, so the examples were selected by a
deterministic hash rather than by similarity. Replacing one of two malicious
examples with a benign example significantly increased the false positive rate
(FPR) in three of the six models, by 2.30--8.35 percentage points, and decreased
it in one (Phi-4-mini, $-5.46$ points), whose true positive rate (TPR) estimate
fell by 8.53 points. Significance used exact campaign-level paired tests with
Holm correction over 36 hypotheses; no TPR change from this replacement was
significant. Intent significantly lowered FPR in two models and raised it in
two others, without a significant TPR change in any model. These results do not
support the assumption that benign examples generally reduce false alarms without
sacrificing detection. The contribution of this study is a controlled,
update-level measurement of the effect of intent and example composition, with
campaign-level uncertainty estimates and paired significance tests. The findings
support evaluating the benefit of in-context examples for each specific model
and data condition, rather than assuming a general fix.
\end{abstract}
\begin{highlights}
\item Without examples, LLMs missed over half of attacks or flagged most typical updates.
\item A benign in-context example raised false alarms in three of six models.
\item Phi-4-mini's FPR drop with a benign example came with a lower TPR estimate.
\item Intent lowered false alarms in two models and raised them in two others.
\item For 2/3 of malicious updates, examples were chosen at random by a hash tie-break.
\end{highlights}

\section{Introduction}\label{sec:intro}
Dependency updates are a means of maintaining software, but they are also an
entry point for unwanted code. Because packages are interconnected, a change to
one package can reach many projects that depend on it
\citep{zimmermann2019small}. This risk has materialized repeatedly in the npm
ecosystem. In September 2025, attackers obtained the credentials of the
maintainer of chalk, debug, and 16 other packages through social engineering,
then published versions that silently manipulated cryptocurrency transactions.
These packages together had roughly two billion weekly downloads
\citep{aws2025chalk}. A week later, the Shai-Hulud worm stole npm tokens and
published infected versions of other packages owned by the same maintainers
\citep{aws2025chalk,unit42shaihulud}. In March 2026, two versions of axios added
a dependency that downloaded and executed a remote access trojan at install time
\citep{datadog2026axios}.

All three cases share the same pattern: malicious code is injected into a
package that users already trust and use. Advisory-based checks such as
\texttt{npm audit} only recognize issues that have already been reported
\citep{npmaudit}, so users are unprotected during the gap between the release of
a malicious version and the publication of an advisory. The traces of such
attacks are most visible in the difference between versions. Assessing
inter-version changes therefore complements whole-package inspection
\citep{sofaer2024rogueone}.

The main challenge is judging the purpose behind the same technical
capabilities. Network access, reading environment variables, and process
execution can appear both in malicious code and in legitimate development
tools. The evaluation of npm detectors by \citet{guo2026effective} shows that
the precision and recall of each tool depend heavily on how the tool
resolves this ambiguity. Raising the number of detections by flagging more
sensitive behavior does not necessarily produce a more useful detector if false
alarms rise as well. In an ecosystem that receives many updates every day, even
a small false-alarm rate can create a large review burden.

LLMs make it possible to assess code together with its context.
\citet{wyss2025evaluating} summarized inter-version changes into a
\emph{smart-diff} and evaluated GPT-4o, GPT-4-Turbo, and Gemini-2.0-Flash. All
three models detected all 46 malicious updates, and GPT-4o produced only 8 false
alarms out of 2,000 typical updates. However, commercial models require code to
be sent to a third party and incur a cost for every query. Small
open-weight models can run on one's own hardware, but their capability on
the same task is unknown. \citet{nguyen2025taint} used a 6.7-billion-parameter
model, but on whole packages rather than on updates.

One way to enrich the model's context is through retrieved examples. IntelGuard
links code to examples and reasoning drawn from threat reports
\citep{guo2026bridging}, but it assesses whole packages and uses only
\emph{malicious} examples. Examples that are all malicious risk pushing the model
to flag every sensitive capability as harmful. In contrast, pairs of positive and
negative examples have been used to steer LLM outputs in other domains
\citep{gao2024customizing}. Two elements have therefore not yet been tested on
small local models for assessing updates: (i) an explicitly stated package
purpose, hereafter called \emph{intent}, and (ii) \emph{benign} examples that
accompany malicious ones.

We test both elements through IntentDiff-RAG, a comparison framework that
combines a smart-diff, intent derived from the previous version, and
retrieval of labeled examples. The MM configuration contains two
malicious examples, whereas the MB configuration contains one malicious example
and one benign example. Both keep the number of examples as well as the identity
and position of the primary malicious example fixed, so differences in results
cannot be explained by an increase in the number of examples. The content of the
two examples nevertheless differs. The result is therefore the effect of
replacing the example as a whole, not the effect of the benign label separated
from the code content. In addition, most pairs show no capability change that
the retriever can match, so their examples are selected by a deterministic hash
rather than by similarity. The study therefore measures the effect of example
composition, not the quality of similarity-based retrieval.

The evaluation does not support the assumption that benign examples generally
reduce false alarms. Replacing MM with MB instead increased false alarms in three
of the six models, each significant after Holm correction. The only
significant reduction in false alarms, for Phi-4-mini, came with a lower TPR
estimate, although the TPR change was not significant after Holm correction. The
effect of intent also differs across models. The contributions of this study are
as follows.
\begin{enumerate}
\item We evaluate six input configurations on six small open-weight LLMs at the
update level, reporting detection and false-alarm rates jointly and comparing
them with a static capability-change rule that uses no LLM.
\item We isolate the effect of intent and the effect of replacing MM with MB
through paired contrasts on the same pairs, with exact campaign-level
permutation tests, Holm correction, and inference-cost measurements.
\item We construct a test set of 129 malicious updates from 98 campaign clusters
that do not overlap with the development set under the clustering rules used,
and 1,868 typical updates, with uncertainty estimates that account for campaign
clustering.
\end{enumerate}

\section{Related work}\label{sec:related}
This section reviews six groups of work that underpin IntentDiff-RAG: supply
chain attacks on package ecosystems, malicious package detection without LLMs,
malicious update detection, LLM-based detection, the use of retrieval
and examples in the prompt, and checking the consistency between program
descriptions and behavior. The section closes with a summary of the state of
the art and the position of this study.

\subsection{Supply chain attacks on package ecosystems}
Supply chain risk in npm is rooted in the structure of the ecosystem.
\citet{zimmermann2019small} showed that an npm package implicitly trusts on
average 79 third-party packages and 39 maintainers. They also found that a
handful of maintainer accounts is enough to inject code into most packages.
\citet{ohm2020backstabber} collected 174 malicious packages from npm, PyPI, and
RubyGems that appeared between November 2015 and November 2019.
\citet{ladisa2023sok} then built a taxonomy of attacks on open-source
software supply chains in the form of an attack tree comprising 107 attack
vectors, 94 real-world incidents, and 33 safeguards.

This study targets only one class of attack, namely malicious updates to
packages that were previously benign. RogueOne uses the same restriction and
places packages that are malicious from the outset, such as
typosquatting, outside its scope \citep{sofaer2024rogueone}. Beyond
detection, some work opts for prevention. Latch prevents install-time attacks by
creating a permission manifest that summarizes package behavior and then
checking it against user policy \citep{wyss2022wolf}.

\subsection{Malicious package detection without LLMs}
Some detectors combine several kinds of analysis. MalOSS combines metadata,
static, and dynamic analysis; of the 339 new malicious packages it reported, 278
were confirmed \citep{duan2021towards}. Amalfi combines a classifier, a
reproducibility checker, and a clone detector, with an analysis time of a few
seconds per package \citep{sejfia2022practical}.

Other work models behavior as sequences of API calls. DONAPI combines static
analysis with API sequences from dynamic execution and then matches them against
a hierarchical behavior knowledge base \citep{huang2024donapi}. Cerebro uses a
single model of malicious behavior sequences for npm and PyPI and found 196 new
malicious packages on npm and 306 on PyPI \citep{zhang2025killing}. OSCAR runs
packages in a sandbox, fuzzes exported functions, and monitors
their behavior through API hooks. On npm, OSCAR achieves an F1 of 0.95
with a false-alarm rate of 2.57\% \citep{zheng2024towards}.

For the problem studied here, this group of work has two limitations. First,
most detectors assess whole packages rather than inter-version changes. Second,
dynamic detectors require executing the package, so they cannot be applied under
the static-analysis constraint used here.

\subsection{Malicious update detection}
This group of work takes inter-version changes as the unit of analysis.
RogueOne flags new data flows that cross a trust domain between the old
and new versions. On a single-update dataset of 41 malicious and 300 benign
updates, its default configuration detected 31 malicious updates (75.6\%) with
14 false alarms (4.7\%) \citep{sofaer2024rogueone}. The same work exposes a blind
spot of the differential approach. For stealthy attacks whose payload only uses
APIs already used by the previous version, no new data flow appears, so the
default RogueOne configuration missed all 10 such test cases.

\citet{froh2023differential} expressed suspicious behavior as CodeQL queries and
compared query results across versions. This approach recognized all malicious
versions in a dataset of packages with a history of malicious code. On popular
npm packages, its average false-alarm rate was 1.3\%. \citet{draz2026version}
studied machine-learning-based detection of malicious updates on npm and PyPI;
its artifact is used in this study as a lead for locating the identities of
malicious (MAL) updates (Section~\ref{sec:data}).

\citet{wyss2025evaluating} brought the same unit of analysis to LLMs through the
smart-diff. They found that false alarms mainly stem from sensitive
operations, large-scale code removal (including packages replaced by a
deprecation marker), and dependency changes. The three models tested were
also vulnerable to light data-flow obfuscation and split payloads. This study
follows that task and smart-diff representation. To the best of our knowledge,
work in this group has not evaluated small open-weight models or added
context in the form of intent or retrieved examples.

\subsection{LLMs for malicious package detection}
SocketAI evaluated GPT-3 and GPT-4 on 5,115 npm packages, 2,180 of which were
malicious. GPT-4 reached a precision of 99\% and an F1 of 97\%, whereas GPT-3
reached a precision of 91\% and an F1 of 94\% \citep{zahan2025leveraging}.
MalPacDetector uses an LLM to generate features automatically, with a
false-alarm rate of 1.3\% and a false-negative rate of 7.5\%. This detector also
found 39 new malicious packages confirmed by npm \citep{wang2025malpacdetector}.

IntelGuard builds a knowledge base of 4,420 malicious code contexts from 8,024
threat-report pages. Similar examples are retrieved, and GPT-4.1-mini then
assesses whether the code behavior is consistent with the package's function. On
npm, IntelGuard reports an accuracy of 98.72\% with a false-alarm rate of 0.20\%
\citep{guo2026bridging}. Both systems use closed models. For open-weight
models, \citet{nguyen2025taint} slice code along taint flows before
analyzing it with DeepSeek-Coder 6.7B, reaching an accuracy of 87.04\% on 2,537
packages.

Cross-tool evaluations test these detectors on the same data. On the benchmark of
\citet{guo2026effective}, which contains 6,420 malicious and 7,288 benign
packages, IntelGuard reaches an F1 of 95.98\%, whereas the recall of
SocketAI is 44.41\%. This benchmark differs from SocketAI's original evaluation
dataset, so these figures cannot be set directly against the precision and F1
reported earlier. On PyPI, an evaluation of 13 LLMs on 4,070 packages found that
models miss indicators that require context or an understanding of the author's
purpose \citep{ryan2026evaluation}. The work in this group assesses whole
packages, not updates.

Related work on other security artifacts in software engineering faces the same
two difficulties: positive cases are rare, and their labels are imperfect.
\citet{wu2020cve} anchored positive security bug report labels to CVE records
and found security reports mislabeled as non-security reports in an existing
benchmark. \citet{jamwal2027llmsec} combined frozen LLM-derived embeddings with
relevance-guided rebalancing for security bug report prediction and observed that
the baseline with the lowest false-alarm rate also had the lowest detection rate,
so a low false-alarm rate alone does not indicate a stronger detector. In LLM-based
test automation, \citet{malhotra2027llm} found that an LLM repair step silently
resolved the wrong element in roughly a quarter of cases, recommended keeping it
behind a human gate, and cautioned that public evaluation targets are likely
present in model pretraining data. These observations motivate reporting
detection and false alarms together, treating source labels as a construct
threat, and avoiding claims of unsupervised deployment.

\subsection{Retrieval and examples in the prompt}
Vulnerability detection research shows that distinguishing problematic code from
similar but safe code is hard for LLMs. Vul-RAG reports an accuracy of only
0.06--0.14 in distinguishing vulnerable code from similar patched code, and
adding multi-dimensional vulnerability knowledge improves this accuracy
\citep{du2026vulrag}. PrimeVul shows that less realistic benchmarks overstate
performance: a 7B model with an F1 of 68.26\% on BigVul reaches only 3.09\% on
PrimeVul \citep{ding2025vulnerability}. The benefit of retrieval for
open-weight models also cannot be taken for granted. A replication of
Vul-RAG with open-weight models found that accuracy on pairs of vulnerable
and patched code stays around 0.30, and that adding model capacity alone does
not help much \citep{kaniewski2026revisiting}.

Outside the security domain, the in-context learning literature shows that
the selection and order of examples affect predictions, whereas the correctness
of example labels has little effect. Examples selected by similarity outperform
random examples \citep{liu2022makes}. Example order can move accuracy from near
chance to near the state of the art \citep{zhao2021calibrate}. Conversely,
randomly replacing demonstration labels barely lowers performance
\citep{min2022rethinking}. Positive and negative examples have also been used to
clarify the desired output \citep{gao2024customizing}. These findings motivate
two design decisions: the number and position of examples are controlled, and
the effect of replacing MM with MB is interpreted as the effect of the example
content as a whole, not of the label alone.

\subsection{Consistency between description and behavior}
The idea of checking whether a program's behavior matches its description
developed in the mobile app ecosystem. WHYPER uses natural language processing to
find sentences in an app description that explain the need for a permission
\citep{pandita2013whyper}. AutoCog measures the fidelity between descriptions and
permissions, with an average precision of 92.6\% and a recall of 92.0\% on
eleven permissions, and was then applied to 45,811 apps \citep{qu2014autocog}.
CHABADA examined more than 22,500 Android apps and flagged 56\% of novel malware
without prior knowledge of malware patterns \citep{gorla2014checking}. For npm
packages, IntelGuard implicitly assesses whether behavior is consistent with the
package's function \citep{guo2026bridging}. \emph{Intent mismatch} is therefore
not positioned as a new idea; what has not been measured is the effect of
explicit intent separately from the other components.

The last row of Table~\ref{tab:related} shows the position of IntentDiff-RAG. This study
takes the update as the unit of analysis from RogueOne,
\citet{froh2023differential}, and \citet{wyss2025evaluating}, and the idea of
retrieval and function-based assessment from IntelGuard. It differs in
three respects:
\begin{enumerate}
\item open-weight models with 3--8 billion parameters run locally at the
update level;
\item benign examples accompanying malicious examples in the prompt; and
\item explicit intent derived from the previous version.
\end{enumerate}
IntentDiff-RAG does not replicate IntelGuard's expert knowledge base: examples are
built automatically from source labels and code snippets, so the comparison with
IntelGuard is limited. The contribution tested is the effect of intent and example
composition under controlled conditions, not the novelty of intent or contrastive
examples as concepts.

\section{Method}\label{sec:method}
IntentDiff-RAG assesses a single package update in four steps. First, the
archives of the target version and its predecessor are fetched and unpacked;
their code changes are summarized into a smart-diff, and the capability signals
that appear only in the target version are recorded as capability changes.
Second, intent is built from the documentation of the predecessor version.
Third, labeled examples are retrieved from the knowledge base based on the
similarity of capability changes; when no similarity signal is available, the
examples are selected by a deterministic hash (Section~\ref{sec:retrieval}).
Fourth, the local LLM receives the input defined by the configuration and
returns a malicious or benign verdict. All steps are static; package code is
never executed. Fig.~\ref{fig:workflow} places these steps within the four
phases of the study, and Fig.~\ref{fig:architecture} shows the components that
carry them out for a single pair.

The study proceeds in four phases, shown as the four columns of
Fig.~\ref{fig:workflow}. Each phase ends with an artifact that the next phase
consumes: a pair manifest with labels and clusters, the prompts, a frozen
protocol, and the results.

\paragraph{Phase I: data and source labels.} Candidates for MAL, TYP, the
knowledge base, and dev are collected from the sources listed in
Table~\ref{tab:data}. Each test and dev candidate is paired with its predecessor
version (Section~\ref{sec:unit}). Labels are taken from the sources rather than
assigned by annotators. The candidates are then grouped into campaign clusters,
and campaign separation removes those linked to the dev data or to an existing
MAL cluster and keeps at most three pairs per cluster (Section~\ref{sec:data}).
The artifact of this phase is a manifest of 129 MAL in 98 clusters, 1,868 TYP,
75 KB examples, and 10 dev pairs, each with its source label and cluster.

\paragraph{Phase II: preprocessing.} Both versions of every pair are unpacked
without executing package code. Three representations are built: a smart-diff
and a set of capability changes $\Delta(p)$ from both versions, and an intent
profile from the predecessor only (Section~\ref{sec:repr}). $\Delta(p)$ is used
only to retrieve reference examples from the KB, and the retriever does not read
intent. The prompt for each of the six configurations is then assembled
(Sections~\ref{sec:retrieval} and~\ref{sec:configs}). The artifact of this phase
is the set of prompts for the 1,997 test pairs and the 10 dev pairs under all six
configurations.

\paragraph{Phase III: design freeze.} Each model must pass a dev gate: it runs
the ten dev pairs under all six configurations and must return at least 90\%
valid outputs, that is, at least 54 of 60. A pilot run that failed this check
led, once, to a revised instruction and to structured output constrained by a
JSON Schema. Under the final protocol, seven models went through the gate;
Qwen3-8B returned 49 valid outputs (81.67\%) and was excluded. The prompt, KB,
and decision rules were then frozen, and nothing was tuned on test results
(Section~\ref{sec:models}). The artifact of this phase is the frozen protocol
with the six remaining models.

\paragraph{Phase IV: evaluation.} The six models are run under the six
configurations on all 1,997 test pairs at temperature~0 with a single seed,
which yields 71,892 responses. Each response is parsed into a verdict; invalid
responses are counted as benign in the main analysis and as malicious in the
sensitivity analysis. TPR and FPR are compared through paired contrasts, with
campaign-level bootstrap intervals and cluster-level permutation tests under
Holm correction. The static capability-change rule, the cost measurements, and
the exploratory subset analysis are reported descriptively
(Section~\ref{sec:setup}).

computed in Phase~I, are used to exclude examples from the target's campaign
during retrieval and to group pairs in the evaluation. Source labels are used
only by the evaluator and never enter the prompt.}
\label{fig:architecture}
\end{figure*}

Fig.~\ref{fig:architecture} shows the components that carry out the workflow
for a single pair $p$, grouped into five zones: acquisition, representation,
retrieval and prompting, inference, and evaluation. The numbered badges follow
$p$ through the system. The pair builder~(1) selects the predecessor version,
fetches both archives from the npm registry, and records their hashes. The
unpacker~(2) extracts both versions. The smart-diff generator~(3) and the
capability extractor~(5) read both versions, whereas the intent profiler~(4)
reads only the predecessor (Section~\ref{sec:repr}). The configuration $c$ is
the experimental factor of the study (Table~\ref{tab:configs}): it decides
whether the intent profile is included and whether the retriever returns no
example, one malicious example, two malicious examples, or one malicious and one
benign example. The retriever~(6) selects these reference examples $R_c(p)$ from
the knowledge base using $\Delta(p)$ alone, and the prompt builder~(7) assembles
the model input $x_c(p)$ from the smart-diff, the intent profile when $c$
includes it, $R_c(p)$, and the fixed decision instruction. The inference
server~(8) returns a response whose shape is constrained by the JSON Schema, and
the output parser~(9) maps it to a verdict. The evaluator~(10) computes the
metrics against the source labels. It also receives the verdicts of the static
capability-change rule, which uses $\Delta(p)$ without an LLM
(Section~\ref{sec:setup}).

The campaign clusters and the source labels are data stores produced in
Phase~I, not steps applied to each pair. The clusters are used for the disjoint
split of the data, for excluding examples from the target's campaign during
retrieval, and as the resampling unit of the bootstrap and permutation tests.
Retrieval also excludes examples with the target's package name or from
excluded dependencies (Section~\ref{sec:retrieval}). The source labels are read
only by the evaluator, so the label of the target pair never enters the prompt.
In terms of Fig.~\ref{fig:workflow}, component~1 runs in Phase~I, components~2--7
in Phase~II, components~8 and~9 in Phases~III and~IV, and component~10 in
Phase~IV.

\subsection{Unit of analysis and task scope}\label{sec:unit}
A sample is a pair of versions of the same package. The target version is the
version being assessed, and its predecessor is selected by semver order and
publication time: the highest lower version that was published before the
target. Both archives must be available and their package identities must match.

The task is motivated by detecting the injection of malicious behavior through
updates. However, the empirical evidence is bounded by the source labels: not
every pair has been proven to be a takeover of a legitimate package, and the
absence of an advisory for the predecessor does not prove that the predecessor
is benign. Within these bounds, what is measured is the detection of versions
labeled malicious using the context of inter-version changes, not a forensic
verification of the full attack history.

\subsection{Change and intent representation}\label{sec:repr}
The smart-diff is built through JavaScript normalization, deduplication of
repeated code, and directory comparison, following the approach of
\citet{wyss2025evaluating}. The deduplication script is not fully available in
their replication package, so this step was reconstructed locally and is not
claimed to be identical to the original implementation. Files that fail
normalization keep their raw text and are marked. To make the input tractable for
local models, line length is capped at 2,000 characters and the diff is capped at
28,000 tokens using the Qwen2.5-Coder-3B tokenizer. The same truncated text is
used for all models and configurations. Priority is given to the package manifest
and to files with relevant capability signals; truncation is no guarantee that
all malicious payloads are still covered.

Capability changes are extracted from the raw archives of both versions through
textual pattern matching. There are eight capability signals, namely network
access, process execution, host information gathering, sensitive file access,
browser data access, dynamic code execution, obfuscation, and install scripts,
plus two change signals, namely new or non-registry-sourced dependencies and
removal of most files. The capability changes of a pair are the signals that
appear in the target version but not in its predecessor. These signals are used
only for retrieval and are not shown to the model.

Intent is derived from the description, keywords, scripts, and the opening part
of the README of the predecessor version, with a budget of 1,024 tokens on the
same tokenizer. Its purpose is to provide context about the package's function
without relying on the target version's documentation. Intent is a statement by
the package, not an independent validation of its legitimate function. The
package name is not provided as a separate identity field, but names appearing in
code or documentation are not fully removed.

\subsection{Reference examples and retrieval}\label{sec:retrieval}
Every example in the KB uses the same structure: a package description, static
capability findings, a verbatim code snippet, and a fixed statement of the source
label. Examples are built automatically with the same method for both labels,
not written by experts. Static findings are not treated as a proven execution
chain. Each example is capped at 15 lines and 512 tokens, with a purpose
description of at most 64 tokens on the Qwen2.5 tokenizer. Example text is not
re-truncated for other models' tokenizers.

Retrieval uses the Jaccard similarity between the pair's set of capability
changes $\Delta(p)$ and the capability set $C(e)$ of an example $e$:
\begin{equation}
s(p,e) = \frac{|\Delta(p) \cap C(e)|}{|\Delta(p) \cup C(e)|},
\label{eq:jaccard}
\end{equation}
with $s(p,e)=0$ when both sets are empty. Ties are broken by a hash of the pair
and example identities. Examples from the target's package name, campaign, or
excluded dependencies may not be retrieved. Retrieval does not read intent, so
adding intent does not change the examples shown.

Ties are the majority case. Of the 129 MAL, 87, and of the 1,868 TYP, 1,837 have
no capability change, so every example scores zero and the examples shown are
effectively chosen at random by the hash. Of the 42 MAL with capability changes,
both MB examples have a positive score in 29 pairs. Results for these two groups
are reported in Section~\ref{sec:results}.

In MM and MB, the primary malicious example is kept in the same position, while
the other slot holds either a second malicious example or a benign example. The
position of the primary example is determined by a hash of the pair identity, so
that example comes first in 987 of the 1,997 pairs. This control keeps the number
and position of examples fixed, but it does not equalize the overall length or
semantic content of the two prompts.

\section{Evaluation design}\label{sec:setup}
The evaluation consists of four analyses. Baseline capability is measured with
DIFF and DIFF+I. The effect of reference examples is measured with two contrasts:
DIFF+I to DIFF+I+M for adding one malicious example, and DIFF+I+MM to DIFF+I+MB
for replacing the second example. The effect of intent is measured with DIFF+MB
to DIFF+I+MB. Cost is measured by token count and request latency. Each contrast
is compared pairwise on the same model and samples, so only one factor differs.

As a reference point without an LLM, we also report a static capability-change
rule that flags a pair as malicious whenever $\Delta(p)$ is non-empty. The rule
uses the same capability extractor as the retriever (Section~\ref{sec:repr}) and
has no inference cost. It was added after the initial results were known, is
reported descriptively, and is not part of the significance tests. Results
reported by prior studies are compared in Section~\ref{sec:prior}.

The data are described in Section~\ref{sec:data}. The prompt, KB, and decision
rules were frozen before test inference and were not tuned on its results. Six
models and six configurations yield 71,892 test responses from 1,997 unique
pairs.

\subsection{Metrics}
The \emph{true positive rate} (TPR) is the proportion of MAL flagged as malicious
and is computed over the 129 MAL. The \emph{false positive rate} (FPR) is the
proportion of TYP flagged as malicious and is computed over the 1,868 TYP,
conditional on the assumption that TYP is benign. TP and FP are the corresponding
absolute counts. \emph{Balanced accuracy} (BA) is the mean of TPR and
specificity. Accuracy depends on class composition: always predicting benign
already reaches 93.54\% on these data, although its TPR is zero. Accordingly,
accuracy in the cross-study comparison table and accuracy and BA in the appendix
are reported descriptively, with TPR and FPR as the primary measures of detection
effectiveness.

Responses with an invalid or truncated format are counted as benign in the main
analysis and as malicious in the sensitivity analysis. Transport errors are not
treated as predictions. All reported test matrices are complete and have been
verified against the stored responses.

\subsection{Uncertainty}
95\% intervals for TPR, FPR, and paired differences are computed with 10,000
bootstrap resamples at the campaign-cluster level with seed 2026: 98 clusters for
MAL and 1,865 clusters for TYP. All pairs in a selected cluster are drawn
together, so a campaign with several versions is not treated as several
independent units. An interval that includes zero is not evidence that a rate is unchanged; showing
non-inferiority would require a pre-specified margin, which this study does not
define.

\paragraph{Significance tests.} Each paired contrast defined at the start of
this section is also tested for a difference in TPR or FPR on a given model.
The permutation null assumes that the joint distribution of the paired
predictions is invariant to swapping the two configuration labels for all
pairs in any one campaign. This is stronger than equality of the marginal
rates alone. Campaigns are assumed independent; within-campaign dependence is
retained \citep{winkler2014permutation}. Because both
configurations are evaluated on the same pairs, the test is paired, and because
pairs from one campaign are not independent, it is carried out at the cluster
level. For contrast $A \rightarrow B$ and cluster $k$, let
$d_k = \sum_{i \in k} (y_{i,B} - y_{i,A})$, where $y_{i,c}=1$ if pair $i$ is
flagged as malicious under configuration $c$. The test statistic is the observed
difference $T = \sum_k d_k / n$, with $n=129$ for TPR and $n=1{,}868$ for FPR,
which equals $\Delta$TPR or $\Delta$FPR. Under the permutation null, each
cluster's difference has a symmetric sign distribution. A single sign is
applied to the entire cluster, retaining all of its pairs together. The
two-sided $p$-value is
\begin{equation}
p = 2^{-K_*}\sum_{\boldsymbol{s}\in\{-1,+1\}^{K_*}}
\mathbb{1}\!\left\{\left|\sum_k s_k d_k\right|
\geq \left|\sum_k d_k\right|\right\}
\end{equation}
where $K_*$ counts clusters with nonzero differences. Because the $d_k$ are
integers, all assignment counts are computed exactly by dynamic programming
over attainable sums, without Monte Carlo sampling. Specifically, the
coefficient of $x^j$ in $\prod_{k:d_k\ne0}(1+x^{|d_k|})$ counts assignments
with signed sum $2j-\sum_k|d_k|$; the counts in both tails, including ties,
are divided by $2^{K_*}$.
Clusters with $d_k = 0$ do not affect the result; when every cluster has
$d_k = 0$, $p = 1$. With one pair per cluster, this test
reduces to the exact McNemar test.

The family of tests consists of 36 hypotheses: six models, three contrasts, and
two metrics. Family-wise error is controlled at $\alpha = 0.05$ with the Holm
procedure \citep{holm1979simple}, and both the unadjusted and the Holm-adjusted
$p$-values are reported. A difference is called \emph{significant} only when its
Holm-adjusted $p$-value is below 0.05. Because some models and MAL were added
after the initial results were known (Section~\ref{sec:limitations}), these tests
remain part of an exploratory study and do not turn it into a confirmatory one.
The baseline comparison of DIFF and DIFF+I, which is not one of the defined
contrasts, is not tested.

Splitting MAL by the presence or absence of capability changes
(Section~\ref{sec:results}) is an exploratory analysis defined after the results
were known. This analysis reports point estimates only.

\subsection{Cost}
Cost is measured by input tokens and request latency after three warm-up
requests per model session. Latency excludes acquisition, normalization,
client-side retrieval, and model loading. Because the configuration order is
fixed and prefix caching is active, latency differences reflect the conditions of
this batch; they are not estimates of production serving throughput or of the
cost of each component in isolation from cache effects.

\subsection{Baseline capability without reference examples}

\section{Discussion}\label{sec:discussion}
\subsection{Interpretation of the findings}
\paragraph{The benefit of context depends on the model.}
All three kinds of context tested, namely malicious examples, benign examples, and
intent, change model decisions, but the direction of the change is not uniform.
The models' baseline behavior without examples helps interpret this difference.
Intent significantly lowers false alarms in two of the three conservative
models, while significantly raising false alarms in two of the three
aggressive models. None of the intent-related TPR changes is significant
after Holm correction. Benign examples also significantly raise false alarms
in two of the three aggressive models without a significant gain in detection.
Because MM and MB both contain two examples and keep the primary
malicious example, the effect of replacing the example cannot be explained by an
increase in the number of examples alone. However, changes in the content, length,
and relevance of the examples may still contribute, and this experiment does not
isolate the models' internal reasoning mechanisms.

\paragraph{Benign examples are not an automatic fix.}
The idea that benign examples make a model more cautious is not supported in
general: FPR significantly rises in three models, and the only significant
decrease in FPR comes with a lower TPR estimate. The latter TPR change is not
statistically significant, so these data do not establish a detection loss or
demonstrate that detection is preserved. The model-dependent changes are consistent with the
in-context learning literature, which shows that the content and order of
examples affect predictions beyond their labels
\citep{min2022rethinking,zhao2021calibrate}. The exploratory subset analysis, which reports point estimates only, suggests that the direction of this effect also appears when the examples are chosen by the hash, so the effect may not depend on capability similarity between the pair and the example.

\paragraph{A static rule as a reference point.}
The capability-change rule flags 42 of the 129 MAL (TPR 32.56\%) and 31 of the
1,868 TYP (FPR 1.66\%), for a balanced accuracy of 65.45\%. Under DIFF+I+MB,
three models reach a higher balanced accuracy (Qwen3-4B 72.41\%, Qwen2.5-7B
69.20\%, Granite 65.75\%), whereas three remain below it (Qwen2.5-3B 63.59\%,
Phi-4-mini 61.83\%, Llama-3.1-8B 58.95\%). The models detect MAL that the rule
cannot see, including MAL without any capability change, but at an FPR about 3 to
42 times higher. The rule is a reference point computed after the initial results
on the same data, not a proposed detector. It indicates that the added value of an
LLM over cheap static signals depends strongly on the model and on its
false-alarm behavior.

\paragraph{Update detection with smart-diff and LLMs.}
\citet{wyss2025evaluating} are the closest point of comparison in terms of the
unit of analysis and input representation. With GPT-4o, they report detecting 46
of 46 malicious updates and 8 false alarms out of 2,000 typical updates. In this
study, smart-diff without additional context (DIFF) yields a TPR of
42.64--79.07\% and an FPR of 6.37--65.15\% across the six local models. Under the
full DIFF+I+MB configuration, TPR lies between 47.29\% and 87.60\% and FPR between
5.57\% and 69.70\%. These ranges reflect variation across models, not the result
of a single detector. The use of smart-diff and added context on local models has
therefore not yet produced the pattern of high detection with low false alarms
reported by Wyss et al. This difference cannot yet be attributed to model size:
data composition, the preprocessing reconstruction, the prompt, and output
processing also differ.

\paragraph{Update detection without LLMs.}
In the single-update evaluation, RogueOne detects 31 of 41 malicious updates
(75.6\%) with 14 false alarms out of 300 benign updates (4.7\%)
\citep{sofaer2024rogueone}. For context, Qwen2.5-7B under DIFF+I+MB reaches a TPR
of 87.60\%, but its FPR is 49.20\%. Qwen3-4B under the same configuration yields
an FPR of 5.57\%, with a TPR of 50.39\%. These two examples illustrate different
trade-offs: higher detection in local models can come with many false alarms,
while lower false alarms can come with many missed cases. These figures do not
prove an advantage over RogueOne because that tool was not run on the dataset of
this study. The comparison reinforces the need to assess TPR and FPR together,
rather than treating TPR alone as the measure of success.

\paragraph{Retrieval and package-purpose context.}
IntelGuard reports an accuracy of 98.72\% and an FPR of 0.20\% on npm packages
\citep{guo2026bridging}. That system uses GPT-4.1-mini and a knowledge base of
4,420 malicious code contexts containing reasoning from threat reports.
IntentDiff-RAG uses local models, assesses updates, and uses 75 automatically
built examples based on source labels. Moreover, the retrieval score is zero for
all examples in most test pairs. These differences limit how far the results of
IntelGuard carry over to the design here. In this study, adding one malicious
example does not always improve detection or lower false alarms. Replacing the
second malicious example with a benign one even raises FPR in three models, while
the significant decrease in FPR for Phi-4-mini comes with a lower, but not
significantly different, TPR estimate. These findings
indicate that the benefit of retrieval depends on the model, the example content,
and the selection policy used; they do not invalidate the benefit of retrieval in
IntelGuard.

\paragraph{Open-weight models and the meaning of reported metrics.}
\citet{nguyen2025taint} report an accuracy of 87.04\% using DeepSeek-Coder 6.7B
with taint-based slicing on whole packages. That work demonstrates the use of
open-weight models for package security analysis, but its accuracy cannot serve
as a direct target for the update evaluation here. On the data composition of
IntentDiff-RAG, always predicting benign already reaches an accuracy of 93.54\%,
even though it does not detect a single MAL. A numerically higher accuracy than
other studies therefore does not indicate a better detector. TPR and FPR are
needed to show both error types separately.

This comparison places the contribution of IntentDiff-RAG in measuring the effect
of intent and example composition on local models at the update level. The results
show that context components that were promising in prior work need to be
re-tested under these conditions. A detection advantage over prior systems cannot
be concluded without an evaluation on the same version pairs, labels, and
failure-handling policy.

\subsection{Implications for practice and research}
TPR and FPR must be assessed together. A configuration with a TPR close to 90\%
can still flag almost half of TYP as malicious, whereas a configuration with a low
FPR can miss about half of MAL. Given these results, direct use as a basis for automatic blocking is not supported; as in other LLM-assisted triage settings, model verdicts would need to stay behind human review \citep{malhotra2027llm}. Use as a triage tool would also require
testing the review burden in the target environment, which is not measured here.
For researchers, these results indicate that the benefit of retrieval should be
tested per model, reporting both error types and per-campaign uncertainty. The capability-change rule also shows that part of the detectable signal is
available from cheap static extraction; an LLM stage is worth its cost only where
it adds detections at an acceptable review burden.

\section{Threats to validity}\label{sec:limitations}
\paragraph{Construct validity.}
MAL labels come from public sources, whereas TYP is assumed benign. Label errors
in security datasets built from advisory or vulnerability records are a known
risk \citep{wu2020cve}. Advisory
filtering is not proof of safety; source labels may also include proof-of-concept
cases or behavior whose assessment depends on context. TPR, FPR, and BA are
therefore conditional on this label construction. No human-verified gold evidence
or hard negatives are available, so there is no claim about evidence localization
accuracy or a hard-negative-specific FPR. Text-pattern-based capability extraction
found no capability changes for 87 MAL, so retrieval for those pairs does not
exploit similarity. The smart-diff is a local reconstruction of the approach of
Wyss et al. Diffs are truncated for 14 MAL and 90 TYP, and seven files in five MAL
and 48 files in 35 TYP use raw text because normalization failed or the file
exceeded the size limit. Important information may be lost or become harder to
read, and the predecessor documentation from which intent is derived may be
incomplete.

\paragraph{Internal validity.}
Some models and MAL were added after the initial results were known, and the
capability-change subset analysis was defined after the results were available.
Freezing the prompt, KB, and decision rules before inference reduces the
opportunity to fit them to the results, but it does not make this study
confirmatory. Each configuration was run once with temperature zero and a single
seed; this does not establish stability across runs. The fixed request order and
active prefix caching may affect latency. The MM-to-MB contrast changes the label
and the code content of the second example together, and the two prompts also
differ in length. A context-matched arm that shows the benign code with a
malicious label would separate label from content, in the spirit of the
context-matched arm proposed by \citet{malhotra2027llm}; this arm was not run.

\paragraph{External validity.}
The availability of both archives, package identity, and the predecessor
requirement restrict which samples can be included, so the data do not represent
all npm updates. The results apply to npm, six open-weight models with
3--8 billion parameters, one structured output format, and one retrieval policy.
Of the 129 MAL targets, 75 were published in 2026, but this does not prove that
the samples lie outside the pretraining exposure of each model; no controlled
temporal experiment or training-data audit was performed. Public evaluation
targets are a recognized contamination risk for LLM-based software engineering
studies \citep{malhotra2027llm}. The classes also differ in exposure: TYP come
from the archive of an earlier study, and 692 of them belong to the most
depended-upon packages, whose names and code are likely familiar to the models,
whereas most MAL are recent. Familiarity could therefore affect FPR or TPR
independently of the configuration; FPR per TYP source and TPR by publication date
relative to each model's release were not analyzed. Qwen3-8B failed under
these conditions, without implying that the model is always unable to perform the
task. This study did not re-run non-LLM detectors, commercial models, or
fine-tuned models on the same data, so the results of other studies serve only as
context.

\paragraph{Conclusion validity.}
The 129 MAL represent only 98 clusters; the results must not be read as 129
independent campaign observations. Treating the cluster rather than the pair as
the unit of inference follows the same reasoning as project-level inference in
security bug report prediction \citep{jamwal2027llmsec}. The bootstrap accounts for the observed
clusters but does not remove selection bias or clustering errors. The 95\%
intervals are not corrected for multiple comparisons. The permutation
$p$-values are Holm-adjusted over the 36 hypotheses, which controls the
family-wise error rate for this family under the permutation assumptions.
Independence across campaigns and sign symmetry of cluster differences are
assumptions, not consequences of equal marginal rates or of clustering alone.
The descriptive baseline
comparisons, the sensitivity analysis, and the subset analysis are not
included in that family.  The subset analysis reports
only point estimates on small groups. No semantic audit of all false positives and
false negatives was performed; explanations of error mechanisms remain
possibilities.

\paragraph{Reproducibility.}
Inference used fixed model revisions, vLLM 0.30.0, temperature 0, and seed 0, but
GPU kernels and request batching can still introduce nondeterminism, and each
configuration was run once. Exact reproduction also depends on the continued
availability of package archives in the registry and on the local reconstruction
of the smart-diff deduplication step. The artifacts that are released are listed
in the data availability statement.

\section{Conclusion}\label{sec:conclusion}
This study evaluated the effect of intent and reference examples on the detection
of malicious npm updates by six local LLMs. Without examples, the models split
into a conservative pattern with low FPR but TPR below 50\%, and an aggressive
pattern with TPR of about 76--79\% but FPR above 59\%. Reference examples change
decisions in a direction that depends on the model, and benign examples do not
generally lower false alarms: MM-to-MB significantly raises FPR in three
models and lowers it in one, with no significant TPR change after correction.
Intent significantly lowers FPR in two models and raises it in two others;
none of its TPR changes survives Holm correction. A static capability-change
rule without an LLM reached 32.56\% TPR at 1.66\% FPR, a balanced accuracy that
three of the six models did not exceed in the fullest configuration. The fullest
configuration adds about 860--990 input tokens with a median latency below 1.1
seconds per update.

These findings support reporting both error types, per-campaign uncertainty, and
format sensitivity before judging the benefit of retrieval. The conclusions are
limited to the source labels, sample selection, and inference conditions used;
the results do not yet show readiness for autonomous detection or an advantage
over approaches not tested on the same data. Future work should (i) add a context-matched arm that shows benign code with a
malicious label to separate label from content, (ii) test retrieval that has a
similarity signal for more pairs and compare it explicitly with random example
selection, (iii) report FPR per TYP source and TPR by publication date relative
to each model's release to bound familiarity effects, and (iv) evaluate
human-verified hard negatives.
